Overhead Flights

頭頂航班：把真實飛航資料放進 macOS 螢幕保護程式——安靜顯示正飛過你頭頂的最近一班。

Role UI/UX & Product Designer
Focus Research · AI workflow · Integration
Platform macOS Screen Saver
Year 2026

Demo — 實際頭頂航班畫面(BAW8RM,倫敦航線)

Situation

主流 App 都要你主動打開來查；被動單機的方向，硬體圈已經有人做過。

市場結構

現代人一天多數時間黏在手機或電腦前，這款產品是基於這樣的現象，利用螢幕保護程式與航班資訊連結，用最低打擾的方式，讓使用者感受到細微的人與人連結。

市面上不缺追蹤飛機的工具——FlightRadar24、Plane Finder、FlightAware 把整片天空攤成地圖、清單、警示，要你主動打開來查，核心是儀表板。Maker 社群也有人做過硬體：Airframe（樹莓派 + 電子紙）安靜顯示頭頂最近一架，是作者送給住在航道下朋友的禮物。這個念頭本身不是我先想到的。

類型 代表 行為 限制
主流 App FlightRadar24 等 主動查詢、多機地圖 要打開、資訊密度高
Maker 硬體 Airframe 等 被動、單機 要買零件、組裝、佔實體空間

Positioning

空缺不在「頭頂航班」這個念頭，在 macOS 螢保這個交集。

兩軸

查證後的空缺不在「頭頂航班」這個概念，而在交集：macOS 螢幕保護程式 × 真實飛航資料 × 編輯排版。主流 App 商業模式不鼓勵被動螢保；Airframe 證明被動單機方向成立，但是新增實體裝置。軟體螢保沒有直接對應案例——論述必須正面處理 Airframe，不能假裝市場空白。

Data integrity

作品集 mockup 可以很美，但主張若是「頭頂航班」，就必須是 live ADS-B，不能是假 callsign 動畫。資料源用途（非商業／教育／個人）也要查過再寫進 README。

Task

把追蹤 App 才有的即時資料，搬進本來就在發呆的螢保。

目標

把「頭頂正在飛過的那一架」這種原本只在追蹤 App 裡的即時資料，搬進電腦本來就在跑的螢幕保護程式——不開新 App、不加新裝置、不用主動查詢，只換螢保內容，讓使用者在幾乎不被打擾的狀態下，也能感受到細微的人與人連結。

“I decided to build a screensaver that quietly shows flight information, so people feel connected without any effort.”

角色：獨立構思與拍板（方向、視覺、取捨、風險）。AI 協作研究彙整、草稿、實作——規則見下。

Action · AI

四個工具、各司其職，我是每一關的守門人。

協作

沒有丟一個 prompt 等結果。四個工具、各司其職，我是每一關的守門人：

工具 職責
Claude 第一輪發想：拆問題、彙整市場調查、規格草稿、技術取捨初案
Perplexity 查證支撐：找一手文件、論文/研究，核實市場調查與設計論述裡的主張站不站得住腳
Grok 只挑錯：不重做發想；審事實、假設、風險
Cursor 只執行「已通過檢驗」的任務包，不在檢驗前自由發揮

選 Perplexity 做查證工具的原因很直接：一般 AI 回答問題時偶爾會講得煞有其事但查無出處，Perplexity 的回答會附上來源——這讓我可以自己回頭核實，而不是照單全收。這對一份會被檢視的作品集論述特別重要：市場調查裡「空缺在哪」的主張、設計論述裡引用的研究，都需要能被追溯到真實文件，不能只是「AI說的」。

守門實例（不是流程展示，是判斷本身）

  1. 01

    Perplexity MCP 一直 404。 沒有等工具修好、也沒有拿 AI 沒查證過的記憶充數——改成自己開網頁手動查證，把資料補回研究裡。判斷點：工具失靈時，「先求有再求證」跟「乾脆手動做」之間，我選後者，因為這份市場調查最終要撐住「這個空缺是真的」這個主張，禁不起用未查證的資料墊底。

  2. 02

    草稿想把 adsbdb 的 rate limit 寫成一個具體數字。 這個數字沒有一手文件核實過，只是 AI 推測的合理值。我要求「未經一手核實的數字不能寫死」，改成保守用詞（「遠低於官方 1 req/s 上限」這種可查證但不誇口的講法）。判斷點：作品集會被檢視，一個查不到出處的數字比沒有數字更傷論述可信度。

  3. 03

    AI 找到不利先例 Airframe。 比較安全的做法是避而不談、讓讀者以為這個念頭是原創的。我選擇正面處理：承認 Airframe 更早做過「頭頂最近一架」這個概念，把差異收斂成「載體（螢保 vs 硬體）+ 執行（編輯排版 vs 電子紙）」。判斷點：找不到對手不代表贏了；願不願意正面迎戰找到的對手，才是產品判斷力的展示，而不是市場調查做得夠不夠勤。

  4. 04

    視覺定案後，我在文件裡標註凍結。 明確告訴 AI「文字大小/排版已經對了，除非我再說，不要碰」，把 AI 之後的自由度收在資料層與背景效果上。判斷點：AI 沒有「夠好就停」的內建判斷，會傾向持續微調到看不出差異為止；凍結是我主動畫線，不是 AI 自己收斂的。

Principle

AI 加速草稿與實作；通過與否由我決定。

Action · Research & Design

先查證市場是不是真的空，再決定用什麼框架撐住「安靜」。

調查方法
  1. 01

    先定義問題本身，不急著查工具。 缺的到底是「追飛機」這個功能，還是「不用主動查就能被動看見」這種體驗？如果問題定義錯了，後面查再多競品也是白工。

  2. 02

    掃描主流 App 的產品邏輯與載體（FlightRadar24、Plane Finder、FlightAware），確認它們的核心假設是「使用者會主動打開來查」——這個假設本身就是市場結構的限制，不是隨便寫的形容詞。

  3. 03

    補查 Maker／報導／GitHub（Airframe、FlightTracker 等），刻意找對自己主張不利的先例，避免自己說服自己「市場是空的」。這一步是為了讓 S 段的定位句禁得起最直接的反駁：「這不是早有人做過了嗎？」

  4. 04

    一手文件核實 API 條款（airplanes.live 的 rate limit、使用條款），沒有一手來源核實的數字，就不寫進對外文件——寧可用保守、可驗證的措辭，也不要寫一個查無出處但看起來更精確的數字。

  5. 05

    收斂成一句禁得起挑戰的定位句：承認先例存在，把差異壓縮到「螢保這個載體」+「編輯排版這種美學執行」兩點，而不是空泛地說「市面上沒有」。

設計

依據三個框架，各一句，再往下落到具體數字：

  • Calm technology（Weiser & Brown, 1995）：資訊留在注意力周邊，需要時才進中心；原文動機本就是對抗資訊過載造成的焦慮，不只是省注意力。
  • Soft fascination（注意力恢復，Kaplan & Kaplan, 1989）：不費力的輕刺激（如看雲）讓長時間專注後的注意力休息，這是這個產品被放在「待機/鎖屏」情境的理由——它要服務的是休息時刻，不是再多一個要處理的資訊源。
  • Ambient intimacy / social snacking（Reichelt, 2007；Gardner, Pickett & Knowles, 2005）：被動接觸他人存在的象徵物，即使不互動，也能降低孤立感——陌生人的班機悄悄浮現，暗示「這世界上還有人在移動、生活」，像是有人悄悄關心著使用者。

這三個框架怎麼變成實際的視覺決策：

  • 喚醒度由亮度/飽和度決定，色相是次要的（Valdez & Mehrabian, 1994）——這是近黑背景（rgb(0.02, 0.02, 0.025)）+ 銀白低飽和文字的依據，不需要靠「冷色調」這種刻板印象來製造安靜感，直接壓低亮度與飽和度就夠了。
  • 文字層級用比例透明度遞減，不是等差遞減：callsign 0.82 → airline 0.48 → meta 0.34 → monogram 0.28。這個比例遞減對應的是人眼對亮度差異的非線性感知（Weber-Fechner）——在低對比環境裡，等比例遞減能讓每一級差異感覺均勻，而不是靠加大對比硬做出層級。
  • 無卡片、無邊框、無 icon 的極簡疊層（aesthetic-usability effect, Kurosu & Kashimura, 1995）：使用者會把視覺上的克制直接解讀為「這東西不會來煩我」，這對一個要出現在鎖屏/待機情境的產品是硬性要求——使用情境本身就要求「不打擾」。
  • 動效只服務真正的資訊變化：新航班淡入 ≤0.4 秒、同航班更新則無動效、多分鐘週期的 4–6px 防燒屏漂移、尊重「減少動態」系統設定。低喚醒環境裡任何無謂動效都會被感知成干擾，所以只在真的有新資訊時才動。

螢保硬限制：滑鼠或按鍵會直接退出，沒有「點一下展開更多」的中間態，所以不能設計任何依賴滑鼠停留/點擊展開的漸進揭露。因此揭露被簡化成誠實的兩態：

態 行為
無飛機 近乎全黑
有飛機 顯示 callsign／航司／高度／方位；只要仍在範圍內就持續顯示（約 90 秒輪詢更新），離開範圍或無航班才退回全黑

趣味來自事件稀有性（真的有一架經過），不靠互動堆疊或動畫討好；抓不到資料時靜默全黑，不跳錯誤訊息——安靜的失敗方式，也是「不打擾」原則的一部分。

Action · Data & Build

WebView 三次失敗後，整個架構搬到原生。

資料真實性
  • 源：airplanes.live（即時位置）+ adsbdb（航司／航線資訊）。
  • 半徑 40 km、高度門檻、90 秒輪詢——這三個數字是取捨的結果：半徑太小容易長時間全黑（體驗上像壞掉），太大又會顯示明顯不在「頭頂」的班機，違背產品的核心主張；90 秒輪詢遠低於 airplanes.live 公開的 1 req/s 上限，用寬裕的安全邊際換取「不需要擔心被限流」的穩定性，代價是資料不是秒級即時——但這款產品要的是「安靜的環境事實」，不是追蹤儀表板，秒級即時本來就不是目標。
  • 無 GPS 時 fallback 固定座標（本機 Wembley Park），並在文件中說明使用者可自行更改，不是寫死不能改的假設。
  • 已驗證多班真實 callsign，可對照 API 核實——這是整個「頭頂航班」主張的底線：如果班機資訊是假的，整個產品的核心主張就會崩塌。這個產品要給的感受是「真的有一個陌生人此刻正飛過你頭頂」，這份連結必須是真的，否則就只是裝飾。作品集 mockup 可以美，但資料造假就等於主張本身不成立。
  • 定性：非商業／作品集用途；任何未經一手核實的限額數字，寧可保守也不寫死（呼應 A0 的守門實例 2）。

“If the flight data were fake, the whole point of the project would break — the connection has to be real, or it's just decoration.”

技術串接
位置（或 fallback） → airplanes.live（最近一架，90s 輪詢） →（可選）adsbdb 航司／航線 → macOS .saver URLSession 資料 · AppKit 字 · Core Image 背景 → 系統設定 → 自訂螢保

最初的路線是全部用 WebView 處理（畫面、文字、資料請求），在 legacyScreenSaver 這個環境裡連續踩坑，逼著整個架構改道：

  1. 01

    WebView 的 fetch 不可靠——同一份程式碼在一般瀏覽器正常，在螢保環境時常靜默失敗，沒有明確錯誤可抓。改法：資料請求全部改用原生 NSURLSession。

  2. 02

    WebView 文字動畫會卡死——requestAnimationFrame 與 opacity 過渡在這個環境會凍結不動，導致文字淡入效果直接失效。改法：文字改用原生 AppKit NSTextField，動效交給 AppKit 自己的動畫機制處理。

  3. 03

    WebView 背景常常不畫出來——整個畫面偶爾只剩空白，背景層完全不渲染。改法：背景改用原生 Core Image（Etheral Shadow 風格：灰階遮罩 + 扭曲 + noise）。

三個坑加起來的結論是雙層原生：AppKit 文字 + Core Image 背景 + URLSession 資料，WebView 整個退出主路徑。這個決定的代價是失去了「用網頁技術快速迭代畫面」的彈性，換來的是螢保環境下真正穩定可用——只替換螢保內容本身，不改使用者在系統設定裡自訂的啟動等待時間。

Action · Ship

作品要能被朋友裝起來，不是只能在自己的 Mac 上跑。

交付
  • GitHub public：rowanlin801229/overhead-flights ——選擇公開而不是私下分享，是因為作品集主張「資料是真的」，公開原始碼讓這句話可以被檢驗，不是單方面宣稱。
  • macos/build-and-install.sh：一鍵建置安裝腳本，設計對象是「有 Xcode 但不熟這個專案細節的朋友」，不是只有我自己看得懂的內部工具。
  • README 三步驟 + Gatekeeper 處理：因為專案未經開發者簽名，macOS 會擋下未簽名程式，README 必須把繞過 Gatekeeper 的步驟寫清楚，不能假設使用者知道怎麼處理這個警告。
  • 作品集資產：主形象 mockup、overhead-flights-demo.mp4（實際拍到一班有完整航線資料的 BAW8RM）、hero 靜態圖，選這段畫面是因為它同時展示了呼號、航空公司、出發地→目的地、高度與方位——都是真實資料，不是排版佔位。
Result

安靜的環景顯示，不是儀表板。

成果

安靜的 ambient display：不靠打斷搶注意力；有飛機時給克制提示，沒有就全黑。把「頭頂有飛機」變成可被注意、不強迫接收的環境事實。

學到什麼

  • 陌生執行環境（legacyScreenSaver）不能假設 Web 技術棧行為照搬——應更早做技術驗證。
  • 找不到直接對手 ≠ 贏了；找到 Airframe 後仍願意正面處理、論述站得住，才是產品判斷。
